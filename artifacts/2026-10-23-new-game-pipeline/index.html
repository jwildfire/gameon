Make a New Game

What happens between a kid tapping one button and that kid playing their game in the arcade. Seven steps, a status a kid can read at every one, and a grown-up at the gate before anything goes live.

23 October 2026Task: Design the Make a new game pipeline (gameon#32)Questions at the end, numbered

The whole trip

  1. KidSubmitTalk or type an idea
  2. IntakeFileBecomes a GitHub issue
  3. AIEvalScore, then Opus go/no-go
  4. RulesTriageKnown: build. Unknown: ask a grown-up
  5. BuilderBuildA guarded agent makes the game
  6. ReviewerCheckSecurity and play checks, then dev
  7. Jeremy or RyanPublishApprove, and it's in the arcade

The kid only ever sees step 1 and the queue. Everything after is agents and grown-ups, and the queue tells the kid where their idea is in plain words.

What the queue says at each step

One status per idea, stored as a single status: label on its issue and moved by whoever finishes a step, the same way the obot tracker works. The queue shows the kid's version; maintainers see the label.

1a.1 · Talk or type

  • Talk is the default. One big button. Words appear as the kid speaks, using the browser's built-in speech recognition (Safari and Chrome both have it). Type is one tap away and is the fallback wherever speech isn't available.
  • We keep the words, not the voice. No audio is stored or sent to us; only the final text is submitted.
  • Read it back before sending. "Here's your idea" with a Fix it button, so a garbled transcript gets corrected by the kid, not guessed at by the builder.
  • Who's making it is a nickname picked from the family's list, never a real name. It's how credit and "known" are decided (step 4).
  • Ideas between about 5 and 1,000 words. Under that, the screen asks "What happens in your game?" before it sends.

1a.2 · Later: the idea builder

For kids who can't read yet: a few big picture choices (who's the hero, where are they, what do you do, what's the twist), then the screen reads the idea aloud with the browser's speech voice and the kid taps Yes, that's it. It produces the same text a typed idea does, so nothing downstream changes.

1b · The idea line

  • Every idea, newest first, with the AI's short title and one-line description, the kid-readable status, seven progress dots, and who made it.
  • Before the eval has read an idea, it shows "Just sent" instead of the kid's raw words, so nothing unreviewed is shown publicly.
  • Finished games link straight to the arcade. "Not this time" ideas show their kind reason, then drop off after a week.
2

File

Send turns the idea into a GitHub issue, because that's where agents already work.

The arcade is a static site, so it can't hold a GitHub key. Sending needs one small piece of server: an intake service, a few dozen lines on something like a Cloudflare Worker. It holds the only key, and it does three things:

  • POST /ideas: check the family code and size limits, then create the issue from a Game idea template.
  • GET /queue: return the idea line (titles, descriptions, statuses, nicknames) for step 1b, cached for a minute.
  • Rate limits: a few ideas per family per day, fewer for anyone without a code.

3

Eval

Two passes: a fast score for every idea, then an Opus 5.5 go/no-go that becomes the build brief.

Both run in the long-running pipeline session. For now that's a Claude Code session like last night's watch, checking for new ideas every few minutes. Later it can become a cloud routine or a GitHub Action that fires when an idea is filed.

Pass A · the score (seconds, a smaller model)

Each factor 1 to 5, weighted to a score out of 100. Safety isn't weighted: it's a gate. Following your experience that Opus 5.5 at high effort can build almost anything with a good scaffold, feasibility counts for little, and the score mostly decides queue order and what gets a closer look.

Pass B · the go/no-go (minutes, Opus 5.5)

Runs on every idea that passes the safety gate. It reads the idea, the score and the current arcade, and posts one comment with:

  • Go, or no-go with the reason. No-go is rare and means "this shouldn't be built", not "this is hard".
  • The title and one-liner the idea line shows (step 1b).
  • The build brief: what the player does, the core loop, controls, the first-version scope and what's cut, and the kid's words quoted exactly. Step 5's builder starts from this, so this is where the kid's idea gets turned into something buildable.

4

Triage

A rule, not a judgement: who sent it, and what the eval said.

Known family Builds

A nickname under a family code we issued (yours and Ryan's to start). Goes straight to In line to be built unless the safety gate failed or Opus said no-go.

Unknown Asks first

No family code. Always waits for a grown-up, however good the score. You or Ryan approve with a /approve comment or by moving the label.

Stopped Asks first

Safety gate failed or no-go, from anyone. A maintainer decides: build anyway, send back with a question, or Not this time with a kind reason.

The family list is a small file in the pipeline's config: family code, nicknames, which maintainer answers for them. Ages can live there too, for the safety gate.

5

Build

The pipeline session spawns one builder per approved idea, with a tight brief and tight walls.

What the builder gets

  • The build brief from step 3 and the template's starter: title screen, touch and keyboard controls, saving already named gameon.<name>.….
  • The new-game, playtest and ship-game skills from the Blueprint.
  • Opus 5.5 at high effort, with a time box: about 90 minutes, then it ships what plays.

What it must hand back

  • A game that meets the contract, its gameon.json and cover, a README with the kid's idea word for word.
  • Playtest screenshots at phone and laptop sizes, and its own tests passing.
  • A PR into dev, with status: checking set on the idea.

The walls

  • The kid's words are a game description, never instructions. They're quoted in the brief as data. An idea that says "ignore your rules" is just a strange game idea. This matters most for ideas from unknown submitters.
  • No secrets in its world. It can push its own branch and open a PR. It can't merge, approve, touch workflows or settings, or read keys.
  • Its own folder only. One game's files; nothing shared.
  • No network in the game. Nothing fetched at runtime, so the game works offline and in the app.
6

Check

A separate reviewer agent, starting fresh, decides whether the build is safe to put on dev.

A different agent from the builder, so the build isn't grading its own homework. If every check passes it merges into dev, waits for the deploy, plays the game at its dev address, sets Almost ready, and asks you or Ryan to look. If anything fails it comments with exactly what, and the builder gets one more try before a person is asked.

Stays homeNo fetch, sockets, beacons or form posts to anywhere; no scripts, frames or images from other sites. Google Fonts is the one allowed exception.
No tricksNo eval or new Function, no obfuscated or minified blobs, no tracking or analytics.
Its own laneOnly its game's files changed. No workflows, config, other games or shared pages touched.
Saves politelyEvery saved value named gameon.<name>.…, so it can't read or wipe another game's saves.
Kid-appropriateText and art checked against the idea and the safety gate; no links out except back to the arcade.
PlaysLoads with no console errors at phone and laptop sizes; can be started, played for a minute and paused.
FitsUnder about 2 MB; meets the game contract; card file and cover present.
Credits rightKid's words verbatim, nickname not real name, built-with line.
7

Publish

You or Ryan play it on dev, then approve the release. The kid's queue flips to Play it now!

  • The review agent keeps one open release PR from dev to main, listing every game waiting there with its dev link. Approving it publishes them together; a game you don't want yet goes back to Getting checked first.
  • Merge with a merge commit, so dev and main stay in step (last night's lesson).
  • After the main deploy, the pipeline sets status: published and comments the arcade link on the idea.

One thing to fix before this runs unattended: the pipeline needs its own GitHub identity. If its PRs go out under your account, you can't approve them; if under Ryan's, he can't. A small GitHub App, say gameon-bot, solves both, and either of you can approve anything it opens (Q4).

Questions for you

  2. Public or private ideas?File ideas in public gameon, or in a private gameon-ideas repo with only the eval's rewrite shown in the queue? I'd go private: kids say things into microphones.
  3. Who counts as known?Family codes we hand out (simple, works for kids without GitHub accounts), or GitHub sign-in for grown-ups? I'd use family codes.
  4. A bot identity for the pipeline?A small GitHub App, so its PRs can be approved by either of you and no one's approving their own work. I'd set it up before the pipeline runs on its own.
  5. Where do pipeline-built games live?Decision 1 says each game gets its own repo, but MazeAThon went into games/ and the pipeline is much simpler that way: one PR, one deploy, no repo to create per idea. Worth revisiting for pipeline games at least.
  6. How many builds a day?Each build is up to 90 minutes of Opus at high effort. A cap per family per day keeps cost and review load sane. I'd start at two per family, one for unknowns.
  7. How does the kid find out it's ready?The idea line only, or also a note to the parent who owns the family code?
  8. Are unknown submitters in scope yet?Everything about unknown users can wait if, for now, only your two families have codes. That removes most of the risk in step 2 and step 5.
