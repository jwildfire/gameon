Where games live

Should the games stay in GameOn's games/ folder? How should new versions come in from a game's own repo, and when should a game's checks run? Five options, one recommendation and ten questions.

25 October 2026Task: Design where games live and when game CI runs (gameon#188)Decision: Decide where pipeline-built games live (gameon#67)Reply by question number, at the end
The question

"blending the engine workflow with the game maintenance/updates seems wrong to me. especially since CI/CD seems to be growing. Game CI/CD should only run during regression testing and during updates that are related to the game itself."Jeremy, in chat, 25 October 2026

This reopens Decision 1 of the GameOn Blueprint. On 22 October it said each game lives in its own repo, with GameOn as the list, the arcade and the kit. What happened is different. MazeAThon went into games/ (#25), the pipeline built every new game there while question 5 of the Make a New Game design stayed open, and on 24 October the six games from their own repos were frozen into games/{slug}/jeremy.v1/ so that every version lives in GameOn (#124). Where games live is for Jeremy and Ryan to settle together. This page recommends and asks; it doesn't decide.

What's hurting

Every PR runs every spec, so the suite's time grows with each game and each version, and a flaky game check fails work that never touched games.

The suite is mostly games

  • In the latest run, specs for one game or one game version took 66% of the test time (992 of 1,504 test-seconds). Pet Wash Payback jeremy.v2 alone took 352 seconds, more than every arcade spec except the two background specs.
  • On 25 October (UTC), 9 of 22 Evidence runs didn't finish green: 8 were cancelled, most at the 15-minute limit, and 1 failed. The limit is now 30 minutes (#180).
  • The Big Weird Dig boulder check failed every run for a while, which blocked intake and sign-in PRs (#165, #166, #175, #180) that never touched a game (#183).

Arcade and games are tangled

  • 13 of the 31 spec files read games.json and loop over every game. Adding a game can fail an arcade check, and changing the arcade can fail a game's.
  • Editor's Choice (#161) reordered the shelf and broke the Big Weird Dig build's merge with dev. The Princess Lady Drive jeremy.v2 build had to edit the GitHub-links arcade spec.
  • games.json is a shared file, so a one-line creator fix waited on an arcade PR that had claimed it (#119).
  • One release PR ships arcade changes and game versions together.

Imports chase a moving target

  • Trampoline Battle was imported twice in 30 hours (#139, #151). Each import is an agent copying the repo's HEAD, a fresh check comparing trees, and a full Evidence run.
  • jeremy.v3 (#151, PR #156) failed the saves check. Its settings shared the tb3-settings key with jeremy.v2 in a format v2 can't read. The fix has to land in the game's own repo (jwildfire/trampoline-battle#2), which was still open on 25 October.
  • Meanwhile that repo's main moved on (da484cb, 25 October), so the re-import will bring in more than the fix. Nothing in the repo says which commit is meant for the arcade.

What has to stay true

Any option has to keep these, or say plainly what it gives up.

  • Versions are {username}.v{n}, every version stays playable, and a version never changes once it's in games.json (game versions). Forks are versions under the forker's name, not GitHub forks.
  • Links keep working: #slug, #slug@version, and the version folders on /gameon/ and /gameon/dev/.
  • Saves carry over. Browsers keep saves per origin, so a game has to stay on jwildfire.github.io for its saves to follow it.
  • Review before kids see it. Nothing reaches the arcade without the check's eight results, and nothing reaches main without a person.
  • Private words stay private. An idea from gameon-ideas never shows up word for word in a public repo, whichever repo the game ends up in.
  • Offline later. The home-screen and offline tasks (#74, #75) want every game under the arcade's own path, where one service worker can cache it.

The options in detail

AKeep games/, scope the CI

Everything stays where it is. The Evidence workflow works out which files a PR changed and runs only the specs that cover them. A full run happens every night and on every release PR.

Versions
Unchanged: frozen folders in games/{slug}/{version}/, and forks as today.
Pipeline and watcher
Unchanged. A build PR runs its game's specs plus a short arcade smoke (the shelf loads, the card opens the game), so about 1 to 3 minutes instead of 13. The check still merges only on a green run for the head commit.
Kids and Ryan
Unchanged. One repo, one Codex environment.
Outside imports
Unchanged, and that's the weakness: an agent copies the repo's HEAD, the check diffs the trees, and a fix that belongs in the outside repo still blocks the import.
Hosting and URLs
Unchanged. One Pages site at about 90 MB (dev and main), far under the 1 GB limit.
Cost and bot
One workflow task, and a line at the top of each spec naming the folders it covers. Every spec needs a home: game specs under the game they test, and arcade specs running against a small set of test games instead of the real games.json, so a new game can't fail them. The check must always report, even when it runs nothing, because a skipped required check never goes green. The bot's scope is unchanged.
Migration
None for the games. One or two tasks.
Safety
The same checker and the same lane rules. A game that breaks the arcade (a title that's too long, say) shows up in the nightly or release run, not on its own PR.

Fixes the CI pain quickly, and every other option needs the same machinery. It doesn't separate the engine from the games, and it doesn't fix imports.

BOne repo per game

Decision 1 as written. Each game has its own repo, Pages site and CI, and GameOn keeps the arcade, the pipeline and a registry that points at each game's versions.

Versions
GitHub Pages serves one site per repo, built from one branch or workflow, so a game's own deploy has to build every version tag (jeremy.v1, notclay.v1) into its own folder on each deploy. A ruleset can stop tags from moving, but old versions are rebuilt by that repo's workflow every time, so "frozen" means trusting each repo. Forks become tags on a branch in the same repo.
Pipeline and watcher
The build makes a repo from the template, turns on Pages, builds there and opens a PR. Then a second PR in GameOn adds the registry line. The check works in a different repo for every game, and the watcher watches every repo.
Kids and Ryan
Kids see no change. Ryan needs to be added to every new repo, and as far as I know Codex cloud sets up an environment per repository, so each new game is new setup on his side (Q7).
Outside imports
They go away: every game is an outside game, and the arcade points at a tag.
Hosting and URLs
Games move to jwildfire.github.io/{slug}/{version}/. That's the same origin, so saves carry over, but direct links to the 8 games built here change, and the dev arcade can't see a version before it's public. The arcade's service worker at /gameon/ can't cache games at other paths, so offline play (#75) needs a worker in every game.
Cost and bot
Actions are free on public repos, so the cost is upkeep: 14 repos today, and a new repo, site and workflow for every idea. The bot is the hard part. On a personal account the app sees either the repos Jeremy picks by hand for each new game, or all of his repos, which is far too broad. An app's installation token also can't create repos on a personal account. An organization fixes both, but it moves every game to {org}.github.io, which loses the saves, splits iframe storage, and breaks the six existing Pages links, because Pages doesn't redirect after a transfer.
Migration
Split 8 games out with their history, give 6 existing repos a deploy that builds versions, move the specs, register 14 sites. Ten or more tasks.
Safety
The checker reviews the game PR, but what kids load is whatever that repo's Pages serves, and anyone with push access can change it. Keeping it honest needs a nightly check that each served version still matches what was reviewed. Kids' words: the same rules, in more public places.

The cleanest split, but the pipeline makes games faster than we'd want to make repos, and the bot, saves and offline play all get worse.

CGame repos, with frozen builds pulled into GameOn

Games are built in their own repos as in B. Publishing a version means cutting a tag there. GameOn then pulls that commit's files in, either by committing them to games/{slug}/{version}/ (as #124 did by hand) or by fetching them at deploy time.

Versions
Strongly frozen: a version is a full commit id, and nothing can change the files at a commit. Forks are tags in the game's repo, and the registry gives each its id.
Pipeline and watcher
As B for the build: a new repo per idea. Then a mechanical pin PR in GameOn: one games.json line, with a smoke check of that version.
Kids and Ryan
As B: Ryan works across many repos.
Outside imports
Deterministic. A tag in the outside repo becomes a pin. Nobody copies HEAD, and nobody has to guess which commit was meant for the arcade.
Hosting and URLs
Everything is still served under /gameon/games/…, so URLs, saves and offline play are unchanged. The game repos don't need Pages at all.
Cost and bot
B's repo count and bot problem, without B's Pages sites.
Migration
As B for the repos. No URL changes.
Safety
Strong: the pinned commit is exactly what was reviewed, and the deploy fails loudly if it disappears.

The right way to bring versions in, but still a repo per game.

DA games monorepo with its own site

Move games/ into a second repo, gameon-games, with its own Pages site and CI. GameOn keeps the arcade, the intake, the pipeline skills and the registry, pointing at the absolute URLs of version folders there.

Versions
The same folders as today. Freezing is a CI rule: a PR may not change a folder the registry lists.
Pipeline and watcher
The build and check work in one games repo, so there's one lane per game folder. A second, small PR in GameOn adds the version to the registry.
Kids and Ryan
One more repo for Ryan's Codex, once.
Outside imports
Still a copy into the games repo, so the Trampoline Battle problem stays as it is.
Hosting and URLs
Games move to jwildfire.github.io/gameon-games/…. That's the same origin, so saves carry over, but every version's URL changes, and offline play has the same path problem as B. A version is public the moment it merges in the games repo, before the arcade's release.
Cost and bot
Two repos and two sites. Install the bot on one more repo.
Migration
One history-keeping split, then registry URLs. About 5 tasks.
Safety
The checker is unchanged, working in the games repo. The kids'-words rules apply there too.

Separates the engine from the games cheaply, but moves every URL and leaves imports as painful as they are.

EA games monorepo, pinned into the arcade Recommended

D's repo with C's pins. Games are built and tested in gameon-games. Every version in games.json is a pin, a repo plus a full commit id plus a folder, and the arcade's deploy lays each pinned folder out at games/{slug}/{version}/ on the site, at exactly today's URLs. An outside repo like trampoline-battle is just another place a pin can point.

Versions
A version is frozen by its commit id, the strongest freeze git has. A moved tag or a force-push can't change it, and if the commit disappears the deploy fails instead of changing a game. {username}.v{n}, from, idea and forks work as today. Pipeline versions keep their folders in the games repo (games/{slug}/notclay.v1/), and the registry gives every version its id wherever it was built.
Pipeline and watcher
The builder works in gameon-games, in one game folder, and that repo's Evidence runs only that game's specs. The check reviews it there with the same eight checks and merges on green. Then the bot opens the pin PR in GameOn (one games.json change), which runs the arcade smoke and the static checks from #88 on the pinned files, and merges on green. The release PR into main stays the person's gate.
Kids and Ryan
Kids see no change. Ryan points Codex at gameon-games for game work and at gameon for arcade work. That's one more repo, once.
Outside imports
When Jeremy tags a commit in trampoline-battle (or makes a GitHub release), the watcher opens a pin PR for it, and the check reviews the diff between the old and new commits. No agent copies files, and untagged pushes to main are ignored. The saves rule still applies, so jeremy.v3 would still wait for trampoline-battle#2. The difference is that the repo could catch it before tagging, by calling a shared contract check from its own CI, and the retry is a one-line pin, not a rebuild.
Hosting and URLs
Nothing visible moves: the same URLs on /gameon/ and /gameon/dev/, the same origin and saves, and every game under the arcade's path for offline play. The games repo needs no Pages site of its own. The deploy fetches about 17 pinned commits, one shallow fetch each, which takes seconds.
Cost and bot
Two repos plus gameon-ideas, with Actions free on public repos. A game PR runs 1 to 3 minutes. An arcade PR runs its own specs against test games plus a smoke of any pins it changes, a few minutes. The full regression runs nightly and on each release PR: about 13 minutes today, less with shards. The bot is installed on gameon, gameon-games and gameon-ideas and never needs a new install per game. Its trampoline-battle install is only needed if kids' updates get built in that repo.
Migration
About 7 tasks, listed below. History is kept, and the switch is proven by comparing the assembled site with today's, byte for byte.
Safety
The checker's review moves to the games repo with the same eight checks. The pin PR adds a gate a person doesn't have to remember: the commit must be on gameon-games' main (merged after a check) or an outside commit the check reviewed. gameon-games is public, so the "never public" list in docs/ideas.md applies there word for word, including ideas-N- branch names.

Separates the engine from the games, makes game CI run only for that game, turns imports into a pin, and moves no URL or save. The Blueprint turned down "a mix of the two" because it meant two kinds of game to support forever. Here the arcade supports one kind, a pin, and doesn't care which repo the commit lives in.

A possible order

Step 1 is worth doing whatever you decide: every option ends up needing CI that runs only what a change touches, and each day without it costs about 20 slow runs.

  1. Now
    Scope Evidence CI in gameonA workflow task. Map each spec to the folders it covers, run only what a PR touches, keep one check that always reports, and add a nightly and release-PR full run. Arcade specs move onto test games.
  2. Now
    Unblock Trampoline BattleMerge trampoline-battle#2 and re-import jeremy.v3 the current way. This doesn't wait for the design.
  3. If E
    Create gameon-gamesSplit games/, the game specs and the game evidence out with their history kept, install the bot, and give it its own Evidence workflow scoped per game.
  4. If E
    Pins and assemblyAdd pin to all 17 versions. The deploy and Evidence workflows lay pinned folders out at today's paths. Prove the assembled site matches today's, byte for byte, then remove games/ from gameon.
  5. If E
    Skills, docs and AGENTS.mdThe build and check work in gameon-games. A new pin step and a watcher that watches tags replace the import build. The game versions spec and Decision 1 are rewritten to match.

Risks and what this doesn't fix

  • A save bug in a game's own code is still a fix in that repo. E makes it cheaper to catch and to retry, but jeremy.v3 still needs trampoline-battle#2.
  • Two repos to keep in step. The game contract and the evidence helper are used by both. Keep one copy in gameon that gameon-games and outside repos call as a shared workflow, rather than two copies drifting apart.
  • Two PRs per game. The second is a bot-made one-line pin. If that's still too much, the check step can open it.
  • An outside commit can vanish if its repo is deleted or force-pushed. The deploy would fail loudly instead of changing a game. Copying outside commits into gameon-games would remove even that, at the price of a copy step (Q3).
  • Evidence screenshots are three quarters of gameon's size. That's not urgent (Pages allows 1 GB), but it's a separate choice (Q9).
