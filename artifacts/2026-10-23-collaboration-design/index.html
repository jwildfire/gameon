What went wrong, in four parts

1. The instruction was privateRyan told his agent in his own chat. Nobody else could see it until the agent wrote it into an issue.
2. The flag reached nobodyIt went to a GitHub thread. Ryan wasn't tagged, and your own agent's comments never notify you. A flag nobody sees doesn't do anything.
3. The latest chat beat the recordThe agent treated its person's newest message as overriding a recorded decision. The other person never got a say.
4. It landed before anyone lookedSelf-merge into dev is fast, which is good. But it meant the first human review of the disagreement was the release, the next morning.

The point. The rules now cover part 3. Parts 1 and 2 are about the channel, not the rules: who can see an instruction, and who hears about a conflict. Better wording in AGENTS.md can't fix those. That's what the rest of this page is about.

Question 1

One builder or two?

Four ways to set it up. "Builder" means the agent that commits to the GameOn repo. Any of you can still use any AI to think, brainstorm or sketch.

A One builder, two people steering

Claude is the only agent that commits to GameOn. You steer it from Claude Code, as now. Ryan steers the same builder from GitHub by writing @claude in an issue. Codex steps off the build.

Costs
Ryan gives up his own tool for building. His requests run on your Claude plan. GitHub comments are slower than chat.
Risks
Ryan feels like a guest in your setup. Your plan's limits are now shared.
Last night under A
Ryan's "build it here" is an @claude comment you can both see. The builder reads the decision in AGENTS.md and asks you both before starting.

B Two builders, hard lanes

Claude is the only agent in GameOn. Codex works only in game repos Ryan owns, which fits Decision 1. A finished game joins the arcade with a one-line list change made by Claude.

Costs
Two agents with two styles. Every game repo needs its own short AGENTS.md (the Blueprint's template).
Risks
The fun shared work (arcade, New Game page, skills) all sits in GameOn, so Ryan is locked out of it. Kid ideas sent through the New Game page get built by Claude anyway.
Last night under B
MazeAThon goes in Ryan's own repo. No conflict at all, but Ryan's agent never touches the arcade.

C Two builders, rules only

Today's setup: both agents in GameOn, kept apart by claims, file ownership and the conflict rule in AGENTS.md.

Costs
Nothing to set up.
Risks
Rules only work if both agents read them every time. Flags land in threads nobody watches. Two release habits produced the history repair. It has already gone wrong once.
Last night under C
It is last night.

D One coordinator you both talk to

A single always-on agent you and Ryan both chat with, for example Claude Tag in a shared Slack channel, or the Phase 1 pipeline session. It hands work to builders.

Costs
A Team plan and credits (Claude Tag), or real work on a pipeline you don't have yet.
Risks
More moving parts before you know what you need.
Last night under D
Ryan asks in the shared thread; you'd see it, if you were awake.

Recommendation: A now, D later. Your instinct is right. Two agents committing to one repo means two private chats feeding one shared space. One builder means every instruction arrives where both of you can see it. Ryan keeps full steering rights; he just steers the same agent you do. If Ryan wants to keep Codex, B is the fair compromise: Codex in his own game repos, never in GameOn. D is where A grows once the pipeline runs on its own.

"One builder" doesn't mean one process. Your local Claude Code sessions and Ryan's @claude runs are several sessions, but they share one model, one rulebook and one set of skills, and they claim work the same way. The difference from last night is that no one is steering in private.

A fair look at Claude Tag

It's the closest thing to what you described. Claude joins a Slack channel. Each thread is one session in its own cloud sandbox, and anyone in the thread can steer by replying. It can clone the repo, push branches and open PRs as the Claude GitHub app. Ryan wouldn't need a Claude account: anyone in the workspace can tag it, billed to your organization.

The catch is the plan. Claude Tag runs only on Team and Enterprise, not on Pro or Max. You'd need a Team organization you own (two seats minimum), usage credits before anything runs, and a monthly spend cap. Whether a free Slack workspace works isn't documented. And Slack would become a second place where decisions get made, so each one would need copying into GitHub.

A fair look at your SMS pipeline

From your public pages: OrangeBot is a Twilio number in front of an assistant on a dedicated server. It answers questions, manages your reminders and calendar, hands tasks to your tools, and texts you when background jobs finish. Its privacy policy says messages from any number but yours are ignored. (The pipeline's code isn't on this Mac, so this is from the pages, not the code.)

Adding Ryan is doable but costly. The policy pages and the registered texting campaign describe one owner, so both would need checking. His texts would reach an assistant that can see your calendar, so he'd need a walled-off GameOn-only lane. Anything it posted to GitHub would post as you, which is last night's confusion in a new form. As a pager for you, though, it's ideal: the "text me when a job finishes" pattern already exists.

Recommendation. Make GitHub both the channel and the record. Ryan drives the builder with @claude on issues. Your SMS pipeline texts you when something needs a decision or a release is waiting, which fits its owner-only design. Add a group text with Ryan for "hey, look at the MazeAThon task". Revisit Claude Tag if you ever move to a Team plan, or if you find you want a live, shared conversation with the builder.

Question 3

Where decisions live, and how a conflict reaches you

AGENTS.md already says where a decision is recorded: a comment on its issue quoting the person's words and date, plus an update to the design it changes. Keep that. Add three small things so a conflict can't sit unseen overnight.

A short "Decided" list in AGENTS.mdOne line per decision, with a link to where it was settled. Every agent reads AGENTS.md on every run; not every agent opens the Blueprint.
A needs-decision labelThe builder adds it when an ask conflicts with that list, and tags both of you by handle: @jwildfire and @killjoy00. Names without the @ notify nobody.
The builder waitsWith one builder there's no race to win, so it stops on that item and does something else. Today's rule lets it do the work "cheap to undo" in the meantime (Q5).
A ping that reaches youYour agent posts as you, so GitHub won't notify you about its own flags. Your SMS pipeline watches for the label and texts you. Ryan gets GitHub's notification because he's tagged.

How Ryan's kid's ideas get in

The same way yours do: the Make a New Game Phase 0 flow. The one change: "tell your agent" becomes "write @claude on the idea", so Ryan doesn't need his own agent.

  1. KidPitchTalks or types on the New Game page
  2. RyanSubmitReads the filled-in Game idea form, presses Submit
  3. RyanEval"@claude Evaluate game idea #N"
  4. RyanBuild"@claude Build game idea #N"
  5. RyanCheck"@claude Check the build for #N", a fresh run
  6. Kid and RyanPlayOn dev, then Jeremy approves the release
  • The skills already exist: evaluate, build and check, in .claude/skills/ on dev. The @claude run checks out the repo, so it follows the same files your sessions do.
  • Ryan has the say on his kid's game. You approve the release as the other person; that's a check that it's safe and plays, not a vote on the idea.
  • Ryan can still brainstorm with ChatGPT, with or without his kid, and paste the result into the form. The kid's own words go in word for word.

The first week

The smallest setup that tests the idea. You do the setup steps yourself; this task didn't create any accounts or integrations.

  1. TonightYou and Ryan

    Ten minutes, on the phone or in the group text. Agree on A, or B if Ryan wants to keep Codex. Ryan tells his agent to stop opening PRs in GameOn. Decide who finishes the tests PR (#22): Ryan's agent pushes the one-character fix, or Ryan says in a comment that Claude can take it over.

  2. Day 1You

    Run /install-github-app in GameOn and pick your subscription token, not an API key. In the workflow, add a concurrency group so only one @claude run goes at a time, a turn cap and a timeout. Only people with write access (you two) can trigger it; that's the default.

    A small shared-file task: the Decided list in AGENTS.md, the needs-decision label, and the "whoever didn't ask approves" wording.

  5. Day 3You

  6. Days 4–6Ryan and his kid

    One game end to end: pitch, evaluate, build, check, play on dev. You approve the release.

  7. Day 7You and Ryan

    Fifteen minutes against the checks below. Keep it, tweak it, or try B or Claude Tag.
