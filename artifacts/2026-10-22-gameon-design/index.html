GameOn Blueprint

One home for the games the kids dream up, a workflow that turns a kid's idea into a playable game in about an hour, and a path onto the iPhone.

22 October 2026, revised the same night: games stay in their own reposTask: Draft the GameOn design (gameon#1)Reply by question number, at the end
The bet

AI can make a fun game in an hour. Not in real time, but in an hour.

So the product is the hour: a reliable path from a kid saying "I want a game where…" to that kid playing it, plus one place where every game can be found and played. Roblox gives kids a toolbox. GameOn gives them a game studio that takes dictation.

Decision 1

Where do the games live?

Decided 22 Oct

Each game lives in its own repo. GameOn is the list of links, the arcade, and the skills for building games. When there's an app, GameOn also holds the build that packages the games for the App Store.

Why it fits: each game stays a small project a kid owns, agents working on different games can't collide, and a game can live in anyone's GitHub account, so a friend's family can make games and still appear in the arcade.

Also considered: copying every game into one repo (simpler app bundling, but one crowded place for every agent), and a mix of the two (two kinds of game to support forever).

How the pieces fit

GameOn repo

  • The list: games.json, one line per game naming its repo and the release that's in the arcade.
  • The arcade: reads the list, then each game's own card file, and plays the game in a frame.
  • The kit: the skills for making, importing, testing and shipping games, plus a link to the template repo.
  • The app build (later): fetches each listed release and packages them.

Each game repo

  • The game, deployed to its own address on GitHub Pages.
  • Its card file, gameon.json, and a cover picture, at the root.
  • A README that keeps the kid's idea word for word.
  • Release tags (v1, v2…) cut when a version is ready for the arcade.
  • A short AGENTS.md from the template that points at GameOn's skills.

A game shows up at its own address the moment it's pushed. It shows up in the arcade when its line is added to the list, on dev first and on main after a release.

Decision 2

The game contract

What every game repo needs to be in GameOn. Short enough for an agent to check in a minute, and it's what lets the arcade and the app build treat every game the same way.

  • index.html at the root runs with no server and no internet.
  • Works with touch and with a keyboard, and says whether it wants to be played sideways.
  • Every saved value is named gameon.<name>.…. On the web all the games share one save area, so this matters even with separate repos.
  • gameon.json and cover.jpg at the root, for the arcade.
  • A README that keeps the kid's original idea, word for word.
  • A release tag for each version that goes into the arcade or the app.
// gameon.json, in the game's repo
{
  "name": "trampoline-battle",
  "title": "Trampoline Battle",
  "tagline": "Drop fighters onto a trampoline and bounce the other team off.",
  "credit": "Designed with my kids",
  "idea": "the kid's pitch, word for word",
  "made": "2026-10-21",
  "built_with": "Claude Opus 5.5",
  "minutes_to_first_play": 15,
  "players": "1-2",
  "sideways": true,
  "needs_internet": false
}

// games.json, in GameOn
[
  { "repo": "jwildfire/trampoline-battle", "release": "v1" },
  { "repo": "jwildfire/princess-lady-drive", "release": "v1" }
]

The list could build itself from every repo tagged with a gameon topic on GitHub. I'd keep it hand-written, because it's also where we choose which release of each game the arcade and the app use.

Decision 3

The hour

How a new game gets made, written as the steps the skills will follow. The times are targets, not measurements yet.

  1. 0:00
    PitchThe kid says what they want. It goes into a "Game idea" issue on GameOn, word for word, before any grown-up edits.
  2. 0:05
    First playableAn agent makes a new repo from the template and builds version zero: title screen, controls for touch and keyboard, saving already wired up. It's playable at its own address straight away.
  3. 0:20
    Play and fixThe kid plays and says what's wrong or what's next. A grown-up steers. Each round is one commit, so a bad idea is easy to undo.
  4. 0:50
    ShipCard file, cover, README, a v1 tag, and a one-line PR adding it to the list. It's in the arcade at /gameon/dev/ that night; a grown-up releases it to the main arcade.

The kit, written once in GameOn and used from inside any game repo:

PieceWhat it does
Template repogameon-template: the starter game, the Pages deploy, a blank card file, and an AGENTS.md that points at the skills. Every new game starts as a copy.
new-gameTurns a pitch into a new repo from the template, turns on Pages, and builds the first playable version.
import-gameTurns a game made as a Claude chat artifact into its own repo that meets the contract. Three of the six were made this way.
playtestOpens the game in a browser at phone and laptop sizes, checks for errors, takes the screenshots for the PR.
ship-gameChecks the contract, writes the card file and cover, tags the release, and opens the PR that adds or bumps the game in GameOn's list.

The catch with separate repos is that agents build games in the game repos while the skills live in GameOn. Each tool gets them a different way:

  • Claude Code: GameOn doubles as a Claude Code plugin, like the scaffold marketplace, so the skills load in any repo once it's installed.
  • Codex and ChatGPT: the template's AGENTS.md links to the skill files in GameOn and says when to follow each one.
Decision 4

Getting onto the iPhone

Home-screen app first Recommended

Make the arcade installable from Safari's Share menu, with an icon, full screen, and the games saved for offline play. Works with games in separate repos as-is, because they all share one web address.

  • No App Store, no developer account
  • Every release reaches the phone on its own
A few hours

A real app

A small iPhone app that shows the arcade with every game bundled inside. A build in GameOn fetches each game's listed release, checks it against the contract, and packages the lot for TestFlight or the App Store.

  • Feels like a real app; works on a plane
  • Needs the $99/year Apple developer account
  • Pinned releases mean a half-finished change never ships
  • App Store review is a separate question for later
A day or two for the app, plus the build

Native ports

Rebuild a game in Swift, the way Angry Dudes has started to.

  • Best feel
  • Days per game, so it can't keep up with an hour per game
  • Only for a breakout favorite
Days per game
Later, maybe

Order a game tonight, play it at breakfast

The natural end of "an hour, but not real time": a kid dictates an idea into the app at bedtime, it becomes a game-idea issue, an agent builds it overnight, and in the morning a grown-up checks it at /dev/ and releases it. Not for now, but the steps above are built so this needs no new machinery, only a way to start the agent.

Questions for you

  1. What are new game repos called?Plain names like trampoline-battle, or prefixed like gameon-trampoline-battle? I'd keep plain names, which match the six you have, and mark them with a gameon topic.
  2. How should kids be credited?No names (as Stretcher Bearer now does), first names, or ages like "designed by a 4-year-old"? I'd use no names, with ages where you like.
  3. Is everything public?Every game and the arcade are on public GitHub Pages now. Is there any game the kids would rather keep in the family?
  4. Home-screen app or a real app first?And do you already have an Apple developer account? I'd start with the home-screen app.
  5. Where do new games get built?Keep starting them in Claude chat as artifacts and importing, or build them straight in a new repo with Claude Code or Codex? I'd support both, since the chat path is what's working.
  6. Is your friend's family making games too?If so, their games can stay in their own account and join the list. Should the arcade show who made what?
  7. Does Timed Out belong?It needs the internet and is more history quiz than kid game. Keep it, mark it, or leave it on your projects page only?
  8. What does "an hour" measure?Pitch to first playable, or pitch to shipped? I'd record it in each card file so we can see whether the kit makes it faster.
